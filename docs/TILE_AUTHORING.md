# Layered tile authoring

Suma tiles are one gameplay object assembled from several independent render
layers. Do not deform one universal finished tile for every variant, and do not
destructively join a generated top to a copied block. Reuse the structural base,
replace the surface, and add optional dressing.

This is the production rule:

```text
logical tile (save id, placement, collision)
├── base       required; structural volume; persists when covered
├── surface    required; material/top treatment; hides when covered
├── detail     optional; grass, ferns, leaves, pebbles; normally hides
└── edge       optional; deliberate rim/skirt/trim; persist or hide by design
```

The result is still one `TileDefinition`, one stock item, one placement target,
and one save id. Separate objects are an authoring/runtime boundary, not
separate gameplay pieces.

For copy-ready reference-image prompts covering grass, mossy forest floor,
sand, snow, concrete, planks, stone paving, mud, detail clusters, and unusual
structural tiles, see
[`TILE_IMAGE_GENERATION_PROMPTS.md`](TILE_IMAGE_GENERATION_PROMPTS.md).

## Why this is the default

- Base dimensions, stacking, collision, and save behavior cannot drift when a
  surface model is revised.
- The same authored top can be tested on different side treatments without
  editing its vertices.
- Covering a lower tile has an exact rule: keep the base, hide the surface and
  dressing, then generate a body-coloured flush lid.
- Grass/ferns/leaves remain optional dressing instead of becoming structural
  geometry.
- A recessed plank bed, dune, snow blanket, or flat turf can use genuinely
  different geometry. No height/normal-map trick is required to fake important
  silhouette or depth.
- Source GLBs remain traceable. Their useful top or detail is extracted once;
  generated blocks and helper geometry are discarded rather than propagated.

## Coordinate and size contract

Asset source files use Blender Z-up; values below are shown in Godot Y-up.

| Part | Authored bounds/plane | Rule |
|---|---:|---|
| footprint | 1.70 × 1.70 m | centred on X/Z; exact slot boundary |
| live footprint | 1.00 × 1.00 m | exact Garden Galaxy logical cell; runtime scales X/Z only |
| walk/collision plane | y = 0.0 | gameplay stays planar unless the definition says otherwise |
| base bottom | y = -0.50 | exact stack step |
| standard base top / surface bottom | y = -0.055 | thin terrain shared seam |
| deep constructed base top / surface bottom | y = -0.18 | chunky cap, joint, and cavity seam |
| flat surface top | y = 0.0 | no dome, jitter, or decorative bevel groove |
| raised exposed top | up to y = +0.35 | only when `exposed_top: "raised"`; entire surface must hide when covered |
| recessed exposed top | down to y = -0.18 | only when `exposed_top: "recessed"` |

The authored 1.70 m footprint is retained because the existing art catalog was
built at that size. `TileVisualFactory` applies
`live_tile_size / 1.70` to X/Z while leaving vertical measurements unchanged.
The live size is 1.00 m because Garden Galaxy's logical horizontal cell is
confirmed as 1 × 1 world units. Do not pre-scale a new source to 1.00 m.

The standard `-0.055` seam is not a universal depth limit. It is only the
profile for thin terrain skins. Constructed materials with readable thickness,
deep joints, gaps, or cavities use the standardized deep seam at `y = -0.18`.
Do not crush a deep source into 5.5 cm merely to keep the standard base.

The shared standard assets are:

- `tile_layer_base_standard.glb`: full structural body,
  y = -0.50…-0.055.
- `tile_layer_base_deep_recess.glb`: lowered structural body for deep
  constructed caps, y = -0.50 to -0.18.
- `tile_layer_surface_flat.glb`: flat surface skin,
  y = -0.055…0.0.

Both are generated by
`art_source/blender/build_tile_core_layers.py` from
`art_source/blender/tile_profiles.py`.

## Layer schema

Layered tiles use `render_profile: "layered"` and a `layers` array:

```json
{
  "id": "tile_example",
  "asset_id": "tile_example_legacy",
  "render_profile": "layered",
  "layers": [
    {
      "role": "base",
      "asset_id": "tile_layer_base_standard",
      "material": "earth_mid",
      "cover_behavior": "persist"
    },
    {
      "role": "surface",
      "asset_id": "tile_layer_surface_example",
      "material": "grass_primary",
      "cover_behavior": "hide"
    },
    {
      "role": "detail",
      "asset_id": "tile_layer_detail_ferns",
      "material": "leaf_medium",
      "cover_behavior": "hide"
    }
  ]
}
```

Every layered tile requires exactly one `base` and one `surface`. `detail` and
`edge` may repeat.

### Fields

- `role`
  - `base`: structural block. Exactly one; must persist.
  - `surface`: primary top treatment. Exactly one; normally hides.
  - `detail`: optional readable dressing such as grass clumps, ferns, loose
    leaves, footprints, or pebbles.
  - `edge`: optional material transition, rim, or constructed trim.
- `asset_id`: GLB id resolved from `assets/3d/reworked`, then `final`, then
  `proxies`.
- `material`: optional semantic palette override applied to every mesh in that
  layer. Prefer it for single-material terrain. Omit it when a layer
  intentionally contains several semantic material slots.
- `cover_behavior`
  - `persist`: remains visible below a stacked tile.
  - `hide`: cross-fades away when the tile is covered.
- `scale_mode`
  - `tile_xz` (default): normalize the authored 1.70 m X/Z footprint to the
    live grid.
  - `none`: preserve authored scale; reserve for exceptional non-footprint
    details.
- `offset`: optional `[x, y, z]` local offset in runtime metres. Fix the asset
  origin in Blender instead whenever possible.

`asset_id` remains on current definitions as a legacy compatibility pointer.
The layered renderer ignores it. Do not rely on that fused GLB for new work.

## Receiving a GLB from Luka

You can provide a GLB for a sand top, snow top, grass top, fern group, leaf
scatter, plank set, stone inset, or similar part. State what the model is
intended to represent; it does not need to contain a correct Suma block.

Use this intake flow:

1. **Archive the source unchanged.**
   Place it at
   `art_source/imported/<source_id>/<source_id>_source.glb`. Never overwrite an
   accepted source. Create/update `source_manifest.json` and record its SHA-256.
2. **Classify the useful geometry.**
   - Broad material skin or relief covering most of the cell → `surface`.
   - Local plants, ferns, grass clumps, leaves, stones → `detail`.
   - Plank lip, masonry rim, snow overhang, transition skirt → usually `edge`,
     or part of `surface` when it must disappear as one complete constructed
     top.
   - Generated lower cube/block → discard it. The shared base owns structure.
3. **Write a deterministic processor.**
   Add `art_source/blender/process_<source_id>.py`; hard-pin the source hash.
   Preserve the useful source shape, fix normals/topology, remove hidden
   helpers and generated structural geometry, align it to the 1.70 m contract,
   and print a JSON report with source hash, output bounds, material names, and
   triangle count.
4. **Normalize by role.**
   - A `surface` must meet the cell boundary deliberately. Flat-connected
  terrain reaches the exact boundary with no bevel V-groove. An isolated
  constructed insert may use a tiny authored gap only when its processor and
  seam review justify it; the active sand and snow surfaces do not.
   - A `detail` should have its origin at the tile centre and its contact plane
     at y = 0. Do not add a backing plane or block.
   - Sparse organic detail that exposes a repeated grid may opt into
     `detail_rotation_variants = 4` on its Tile Library manifest. Runtime and
     scalable rendering then choose a deterministic quarter-turn from the cell
     coordinate. Detail is never translated: containment is established while
     authoring and must remain valid in every runtime variant. This varies only
     the detail; the structural shell, authored tile rotation, and connection
     topology do not change.
   - Meaningful recesses, plank steps, seams, and large relief belong in mesh
     geometry. Use albedo texture variation for fine visual lines only; do not
     pretend major depth exists solely through a height/normal map.
5. **Export only the layer.**
   Use `tile_layer_surface_<name>.glb`,
   `tile_layer_detail_<name>.glb`, or `tile_layer_edge_<name>.glb` under
   `assets/3d/reworked/`.
6. **Compose in data.**
   Reference the shared base and the new layer in `data/tiles.json`. “Fuse”
   means runtime assembly into one logical tile—not Blender Join and not a
   copied body embedded in every GLB.
7. **Choose cover behavior.**
   Plants and exposed tops almost always use `hide`. The base always uses
   `persist`. An edge persists only if it genuinely belongs to the structural
   wall when another tile is above it.
8. **Import and test.**
   Run Godot import, the core test suite, then inspect a 3×3 patch and a stack
   under production lighting.
9. **Record provenance.**
   Add the accepted source hash, processor, transformation summary, and output
   layer to `docs/ASSET_PROVENANCE.md`.

The current processors are concrete examples:

- `process_sand_tile.py` ray-samples the useful source dune, regularizes it to
  a smooth height field, discards the generated block, and exports only
  `tile_layer_surface_sand.glb` with flat normals as Asset Studio's 0% value.
- `process_snow_tile.py` configures that extraction pipeline for stronger
  low-frequency geometry smoothing and exports only
  `tile_layer_surface_snow.glb`, also at the flat 0% normal baseline.
- `process_concrete_tile.py` preserves the revised untextured four-panel
  control-joint topology and flat shading, applies no smoothing or remeshing,
  normalizes it to the 18 cm deep-constructed layer contract, and exports only
  `tile_layer_surface_concrete_brutalist.glb`.
- `process_grass_tile.py` and the existing fused `tile_grass.glb` are retained
  as source/history. They are not the active meadow. If the preserved foliage
  is reused, it should be re-exported as a `detail` layer rather than replacing
  the shared base and clean flat surface.

## Geometry choice guide

This section is the decision authority for future tile work. Classify geometry
by what it physically does, not by its material name. "Stone", "snow", "moss",
or "wood" can belong to different roles in different designs.

### Classification order

Apply these questions in order:

1. **Does it change the walk/support topology?** A real hole, bridge opening,
   stair, ramp, basin, cliff, tunnel, or moving hatch is a special structural
   tile and may need custom collision. Do not disguise it as decorative relief.
2. **How deep must the replaceable top be?**
   - Lowest visible point at or above `y = -0.055`: use
     `tile_layer_base_standard`.
   - Readable joints, gaps, cavities, or material thickness extending below
     `y = -0.055` but not below `y = -0.18`: use
     `tile_layer_base_deep_recess`.
   - Deeper than `y = -0.18`: justify a new standardized base profile or a
     special structural tile. Never vertically crush the source just to fit.
3. **Does it cover most of the cell?** It is the `surface`, even if it consists
   of multiple boards, stones, slabs, or cracked plates.
4. **Is it localized and non-structural?** It is `detail`: plants, loose
   objects, stains with geometry, footprints, or scattered fragments.
5. **Does it primarily follow the perimeter or transition between materials?**
   It is `edge`: curb, fascia, rim, overhang, border, trim, or transition skirt.
6. **What happens when another tile is stacked above?**
   - The structural `base` always uses `persist`.
   - Exposed material, plants, loose dressing, and top trim normally use
     `hide`.
   - An `edge` uses `persist` only when it is genuinely part of the remaining
     block wall rather than the removable top.
7. **How do equal neighbours meet?**
	- `full_flush`: continuous terrain should visually merge at the boundary.
	- `tiny_individual_seam`: deliberately separate slabs, boards, pavers, or
	  manufactured modules.
   - `soft_isolated`: a mound, bed, patch, or soft inset deliberately stops
     before the boundary.
	- `merged_surface`: region-level rendering such as connected water.
	- The seam choice is authoritative across tile types: two `full_flush`
	  surfaces consume their shared bevel even when their materials differ.
	  Matching `connection_group` values use the continuous-relief topology;
	  differing groups use the transition topology, which eases both sculpts
	  back to the shared walk plane at the boundary. Only an explicit separated
	  mode may draw a per-cell trench.
8. **Where is the highest usable top?**
   - `flush`: the main walk/support plane is `y = 0`, even when joints descend
     deeply below it. Brutalist Concrete is `flush`.
   - `recessed`: the whole usable exposed top is below `y = 0`.
   - `raised`: meaningful visible relief rises above `y = 0` and the complete
     surface must hide when covered.

`exposed_top` describes the highest usable surface, not the lowest groove.
A flush concrete slab may therefore have 18 cm control joints while remaining
`exposed_top: "flush"`.

### Base-profile examples

| Base choice | Use it for | Typical examples | Do not use it for |
|---|---|---|---|
| `tile_layer_base_standard` (`-0.50..-0.055`) | Thin skins, colour/material changes, shallow organic relief | plain grass, trimmed lawn, dry grass, soil, clay, compact sand, shallow mud, thin snow, frost, moss carpet, ash, salt, smooth asphalt, thin carpet, cork, linoleum | deep gaps between boards, thick slabs, open grates, deep masonry joints |
| `tile_layer_base_deep_recess` (`-0.50..-0.18`) | Constructed or chunky tops whose material thickness is part of the read | precast concrete panels, timber decking, railway sleepers, thick cobbles, flagstones, brick paving, ceramic pavers, metal plates, drain grates, inset mosaics, broken ruin floors | ordinary grass recolours, sparse plants, a single loose rock, stairs or open water |
| New reusable base profile | A recurring depth/shape contract that neither shared base can support | very deep industrial channels, standardized planter beds, repeated sunken pools, thick roof-deck modules | a one-off visual that can fit an existing profile |
| Dedicated structural tile | The tile contains real traversable/blocked topology or a non-solid volume | stairs, ramps, cliffs, pits, canals, bridge spans, caves, elevators, trapdoors, deep ponds | cosmetic grooves, painted cracks, shallow puddles |

### Same material, different role

Use these comparisons when a name alone is ambiguous:

| Material/object | `surface` case | `detail` case | `edge` or structural case |
|---|---|---|---|
| grass | continuous turf covering the cell | several tufts | sod lip at the perimeter |
| moss | continuous moss carpet | localized cushions on stone | mossy transition skirt |
| snow | complete snow blanket | small clumps or footprints | overhanging snow lip |
| sand | walkable dune/ground skin | a few piles over paving | sand drift stopped by a border |
| stone | fitted walkable field | loose rocks | curb/retaining rim |
| concrete | slab field or poured plane | broken chips | curb, channel, or load-bearing wall |
| planks | complete deck | loose discarded board | fascia; bridge span if it crosses a void |
| brick | complete paving field | loose bricks/rubble | border or wall |
| metal | complete plate/grate floor | bolts/scrap | frame, rail, or moving hatch |
| leaves | thick continuous leaf bed | scattered individual leaves | leaf pile caught along an edge |
| roots | cell-wide root mat affecting the top | one exposed root cluster | structural root bridge if traversable |
| water | continuous region-level surface | shallow puddle overlay | basin/canal is structural |

### Hard prohibitions

- Do not use `detail` to provide the walkable plane.
- Do not embed trees, ferns, rocks, or loose decor in `base`.
- Do not use `edge` for a feature that actually occupies most of the cell.
- Do not use a normal/height map to fake a gameplay-readable gap or step.
- Do not keep an AI-generated lower cube when a standardized Suma base fits.
- Do not force every surface onto `tile_layer_base_standard`.
- Do not squash meaningful vertical geometry to 5.5 cm. Select the deep base.
- Do not create a unique base for every colour or material. Reuse the closest
  standardized depth profile and recolour it semantically.
- Do not mark a deeply jointed but level slab as `recessed`; it remains
  `flush` when its primary support plane is at `y = 0`.
- Do not let any hidden top/detail layer persist through a stacked tile.

Use the smallest truthful representation:

- Plain grass/soil colour change: shared base + flat surface + semantic
  material override.
- Sand or snow relief: shared base + sculpted surface.
- Leaves on otherwise normal grass: shared base + flat grass surface + leaf
  detail.
- Fern-covered ground: shared base + flat/sculpted surface + one or more fern
  detail layers.
- Recessed plank bed: shared base whose wall reaches the chosen seam +
  constructed plank surface/edge geometry; declare `exposed_top: "recessed"`.
- Raised rubble or drift: shared base + complete raised surface; declare
  `exposed_top: "raised"` and ensure the layer hides.
- Fine plank grain, hairline cracks, or colour mottling: texture/albedo is fine.
  A gameplay-readable step, recess, silhouette, or gap must be geometry.

Do not deform the same finished mesh into unrelated material families. Share
the stable structural base, but author surfaces according to what they
physically are.

## Materials

Use semantic names from
`assets/palettes/gg_material_palette.tres`. Runtime material overrides are
preferred for one-material layers because they make the data composition
obvious. Multi-material assets should name their Blender material slots
semantically so `MaterialLibrary` rebinds them.

Snow deliberately uses two values:

- `snow_top`: warm, matte, high-value upper blanket.
- `snow_side`: cooler/darker structural side, preserving the block silhouette
  instead of clipping into one flat white mass.
